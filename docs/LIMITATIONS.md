# LIMITATIONS.md — Academic Transparency

This document exists so the project can be presented and evaluated
honestly. It lists what's real, what's simulated, what's estimated, and
what's out of scope for this build.

## REAL

- Map tiles and geographic data: **OpenStreetMap**, via Leaflet.
- Location search: **OpenStreetMap Nominatim** geocoding (any place in
  India you type resolves to real coordinates; subject to Nominatim's
  fair-use rate limits — see below).
- Google / GitHub sign-in: a real OAuth2 authorization-code flow
  (`backend/src/services/oauthService.ts`) — not a mock. It requires you to
  register your own OAuth app with Google/GitHub and put the client
  ID/secret in `backend/.env` (see `docs/SETUP.md` §8); without that, the
  buttons return a clear "not configured" error rather than pretending to
  work.
- All software dependencies: open-source (React, Express, MongoDB, Socket.IO, etc).
- The OCPP 1.6 *message shapes* simulated are based on the real protocol
  spec (message names and field names) — see `docs/OCPP.md`.
- Your own account data: registration, login, vehicle profiles, bookings
  you make, and the resulting invoices/rewards are genuinely persisted and
  computed from your actions (not pre-scripted).
- The booking double-booking prevention logic is a real, enforced
  server-side check, not a UI-only restriction.
- Authentication and authorization are real (bcrypt-hashed passwords, JWTs,
  backend-enforced RBAC) — not cosmetic.

## SIMULATED (clearly not live infrastructure)

- **Charger availability & status** — driven by the seed script and this
  app's own booking/session logic, not real hardware telemetry.
- **Charging sessions** — battery %, energy consumption (kWh), and
  charging power are generated by a server-side timer
  (`chargingSimulatorService.ts`) using a simple linear/taper model, not
  measured from a real vehicle or charger. The model is deliberately
  accelerated (see `CHARGING_TICK_MS` and the `× 6` acceleration factor in
  the tick calculation) so a demo session completes in a reasonable time
  rather than the 20–60+ minutes a real DC fast charge takes.
- **OCPP messages** — see `docs/OCPP.md`. Simulated message log, not a
  certified CSMS or a real OCPP WebSocket connection to hardware.
- **Payments** — `paymentMethod: 'SIMULATED_WALLET'`. No real payment
  gateway is integrated; no real money moves. The `Payment` schema is
  intentionally gateway-agnostic so a real Indian payment gateway (Razorpay,
  PayU, etc.) could be integrated later without changing the booking flow.
- **Historical booking data used for analytics** is genuinely generated by
  real bookings you make in your own session, plus one seeded historical
  example — it is not a large synthetic dataset standing in for real usage
  patterns (see "Not implemented" below re: ML demand forecasting, which
  is where large synthetic datasets would become relevant).
- **Station pricing, ratings, and amenities** in the seed data are
  plausible but fabricated for demonstration — they are not sourced from
  real charging network operators, even though real operator names
  (Tata Power EZ Charge, ChargeZone, Statiq, Ather Grid) are used as
  flavor text for realism. **Do not present seed data as real pricing or
  real station information.**

## ESTIMATED (explicitly labelled as estimates in the API/UI)

- **Range estimate** (`/range/estimate`): `batteryCapacityKWh ×
  (currentBatteryPercentage/100) × efficiencyKmPerKWh`, with a flat 15%
  safety margin. This is a simple deterministic formula, not a
  physics-based or ML range model, and does not account for terrain,
  traffic, weather, HVAC use, or driving style. The API response includes
  `"estimate": true` and `safetyMarginApplied` for exactly this reason.
- **Recommendation score & "why this station" reasons**
  (`/recommendations`): a transparent weighted formula over normalized
  sub-scores (distance, availability, charging speed, price, estimated
  waiting time, rating) — see ARCHITECTURE.md for the exact formula. It is
  explicitly **not** described as "AI" anywhere in the UI, per the
  project's "no fake AI labels on simple logic" requirement.
- **Estimated waiting time**: a flat placeholder (0 min if a compatible
  charger is free, ~15 min otherwise) — not derived from a real queue or
  historical wait-time data.
- **ETA / route geometry**: not implemented in this build (see below).

## NOT IMPLEMENTED in this build (documented gaps vs. the full spec)

The original project specification is large (16 phases, ML forecasting,
full OCPP CSMS, complete admin CRUD UI for every entity, route planning
with a routing engine, refresh-token rotation, email verification, rate
-limited per-route tuning, Playwright E2E suite, etc). This build
prioritizes a **solid, honestly-documented, fully working core demo flow**
over a superficially complete but shallow implementation of everything.
Explicitly out of scope for this build (all straightforward to add later
on top of the existing architecture, without redesigning it):

- **ML demand forecasting** (Random Forest / XGBoost LOW/MEDIUM/HIGH
  output) — not implemented. The analytics module provides real
  aggregation-based statistics (bookings by day, revenue by day, station
  utilization, charger status breakdown) but no predictive model. Adding
  this would live in a new `ml-service/` (as scoped in the original spec)
  or `analytics/` module, trained on the `Booking`/`ChargingSession`
  collections.
- **Real OCPP WebSocket CSMS / hardware connectivity** — see `docs/OCPP.md`.
  Only the message-shape simulation is implemented.
- **Route planning / OSRM-GraphHopper-Valhalla integration** — not
  implemented. The `Station` and `Vehicle` models have the lat/lng data a
  routing service would need; the `range/estimate` endpoint uses a
  straight-line distance as a stand-in for route distance today.
- **Full admin CRUD UI** for every entity (users, stations, chargers,
  bookings, sessions, maintenance) — the backend REST API supports all of
  this (see `docs/API.md`, `/api/admin/*`) and the admin dashboard page
  shows live analytics, but dedicated management screens for editing every
  entity via forms are not built. This can be exercised via `/api/docs`
  (Swagger) or curl/Postman today.
- **Refresh-token rotation / logout blacklisting** — refresh tokens are
  issued but there's no rotation/revocation endpoint; logout is a
  client-side token discard. Fine for a local demo; not production-grade
  session security.
- **Email verification** — the `User.verified` field exists but no email
  is actually sent; seeded users are marked `verified: true`.
- **Forgot-password flow** — not implemented.
- **Automated E2E tests (Playwright)** — documented as a next step in
  `docs/TESTING.md`, with a small pure-function unit test suite in place
  today (`backend/src/__tests__/`).
- **Marker clustering** on the map — not implemented; at the current demo
  data volume (dozens of stations) it isn't yet needed, but is a
  straightforward addition (`leaflet.markercluster`) if the seed dataset
  grows substantially.

## Booking conflict guarantee caveat

The booking engine uses a MongoDB transaction when the database supports
one (a replica set). On a standalone MongoDB instance — common for a quick
local setup — transactions aren't available, and the code falls back to a
non-transactional check-then-insert. Under simultaneous concurrent
requests for the exact same slot on a standalone instance, there is a
narrow theoretical race window. For an academic demo this is acceptable
and clearly documented; for production use, run MongoDB as a replica set
(even a single-node one) or add a unique partial index as a stronger
guarantee — see `docs/ARCHITECTURE.md` and `docs/DEPLOYMENT.md`.
